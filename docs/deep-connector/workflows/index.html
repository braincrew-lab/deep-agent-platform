Deep Connector 반복 업무

이 페이지는 컬렉션 담당자가 되풀이하는 일을 순서대로 정리합니다. 규정이 바뀌면 새 버전으로 교체하는 일, 처리 결과를 다시 만드는 일, 검색 방식을 바꿔 결과를 비교하는 일, 정기적으로 품질을 점검하는 일입니다.

이 페이지에서 할 수 있는 일

  • 새 버전 업로드로 문서를 개정본으로 교체하고 이전 버전을 다시 엽니다.
  • 다시 적재로 처리 결과를 새로 만들고, 그동안 검색에 나오지 않는다는 점을 감안해 일정을 잡습니다.
  • 같은 질문을 검색 방식만 바꿔 실행하고 결과를 비교합니다.
  • 다음 점검 때 같은 기준으로 볼 수 있게 기록을 남깁니다.

개정본으로 교체하기(새 버전 업로드)​

규정이나 설명서가 바뀌면 문서를 지우고 다시 올리지 말고 새 버전 업로드로 교체합니다. 이전 파일이 버전으로 남아 개정 전·후를 대조할 수 있고, 에이전트가 옛 문서와 새 문서를 섞어 답하는 일도 막을 수 있습니다. 문서 업로드·수정 권한(Level2 이상)이 필요합니다.

새 버전 업로드 창

번호메뉴기능이런 때 사용하세요
1파일 선택 영역개정 파일을 끌어다 놓거나 눌러서 고릅니다. 고른 파일 이름이 표시됩니다.개정본을 고를 때
2변경 사유무엇이 바뀌었는지 적습니다(선택, 500자 이내). 변경 이력에 함께 남습니다."숙박비 상한 120,000원 → 150,000원"처럼 남길 때
3취소교체하지 않고 닫습니다.다른 문서를 열었을 때
4교체새 파일로 바꾸고 다시 처리합니다. 직접 고친 청크는 새 처리 결과로 바뀝니다.파일과 사유를 확인했을 때

따라 해 보기​

  1. "규정 Q&A" 컬렉션에서 "출장비-지급-규정.pdf"를 눌러 문서 상세를 엽니다.
  2. 위쪽 새 버전 업로드를 누르고, 창 맨 위 문서 이름과 현재 버전(v1)을 확인합니다.
  3. 파일 선택 영역을 눌러 개정본 "출장비-지급-규정-2027개정.pdf"를 고릅니다.
  4. 변경 사유에 "2027.01.01 시행 개정: 숙박비 상한 서울·수도권 120,000원 → 150,000원, 그 밖의 지역 100,000원 → 120,000원"을 적습니다.
  5. 교체를 누릅니다. "v2(으)로 교체를 시작했습니다. 파싱이 완료되면 반영됩니다." 알림이 나옵니다.
  6. 처리가 끝나면 원본 미리보기 위 버전 버튼을 눌러 버전 목록을 엽니다.

문서 버전 목록

번호메뉴기능이런 때 사용하세요
1버전 버튼지금 보고 있는 버전(예: v2 (현재))입니다. 누르면 목록이 열립니다.이전 버전을 볼 때
2현재 버전교체한 개정 파일입니다. 검색과 에이전트 답변은 이 버전을 기준으로 합니다.개정본이 현재 버전인지 확인할 때
3이전 버전교체 전 파일입니다. 교체 일시와 변경 사유가 함께 보입니다.개정 전 문구를 다시 볼 때
4개정 사항현재 버전 원본에 들어간 개정 문장입니다. 이전 버전을 고르면 "v1 버전을 보는 중입니다" 안내와 함께 옛 원본이 보이고, 구성 단위와 검색은 계속 현재 버전 기준입니다.개정 문장이 원본에 들어갔는지 볼 때

교체가 끝나면 세 가지를 모두 확인해야 반영이 끝납니다.

  • 버전 번호가 올라갔는지
  • 처리 상태가 완료인지
  • 개정 문장이 검색되는지(이 예에서는 RAG 진단에서 "서울 출장 숙박비 상한 금액은 1박에 150,000원이며, 이 금액은 2027년 1월 1일부터 상향 조정된 기준입니다"로 답함)

문서 이름은 교체한 파일 이름으로 바뀝니다. 같은 파일을 다시 올리면 "현재 파일과 동일한 내용입니다. 변경 없이 유지됩니다."가 나오고 버전이 올라가지 않습니다.

처리 결과 다시 만들기(다시 적재)​

파일은 그대로 두고 처리만 다시 하고 싶을 때 씁니다. 파이프라인을 바꿨거나, 분석기를 바꿨거나, 처리 결과가 이상할 때입니다. 문서 목록 행 오른쪽 다시 적재나 문서 상세의 다시 적재를 누릅니다.

다시 적재 확인 창

번호메뉴기능이런 때 사용하세요
1안내같은 파일을 다시 처리하고, 버전이 하나 올라가며, 끝날 때까지 문서가 검색에 나오지 않는다는 안내입니다.운영 중인 컬렉션에서 실행 시간을 정할 때
2파이프라인지금 파이프라인을 유지하거나 다른 파이프라인을 고릅니다.바뀐 처리 방식을 적용할 때
3경고사람이 직접 고친 청크와 요소도 새 결과로 바뀐다는 경고입니다.직접 고친 청크가 있는지 먼저 확인할 때
4취소다시 적재하지 않고 닫습니다. 바로 오른쪽 다시 적재를 누르면 처리를 다시 시작합니다.근무 시간이라 미루거나, 조건을 확인한 뒤 실행할 때

에이전트가 쓰는 컬렉션이라면 처리하는 동안 에이전트도 그 문서를 찾지 못합니다. 질문이 몰리는 시간을 피해 실행하세요.

같은 질문으로 검색 방식 비교하기​

문서는 처리됐는데 원하는 근거가 위쪽에 나오지 않을 때, 문서를 다시 올리기 전에 검색 조건부터 비교합니다.

  1. 실험 > 검색을 엽니다.
  2. 컬렉션 선택에서 점검할 컬렉션을 고릅니다.
  3. 메타데이터 필터와 자유 필터에 남은 조건이 없는지 봅니다.
  4. 시맨틱 검색으로 질문을 검색하고 결과 카드의 문서 이름, 청크 번호, 본문을 메모합니다.
  5. 검색 방식만 키워드 검색으로 바꿔 문서에 쓰인 낱말로 다시 검색합니다.
  6. 정확한 숫자나 코드는 문자열 검색으로 찾아봅니다.

"규정 Q&A"에서 비교한 예입니다.

키워드 검색숙박비 상한출장비-지급-규정.pdf의 숙박비 조항 청크

문장으로 물었을 때와 낱말로 찾았을 때 모두 같은 청크가 나오면 검색 쪽은 문제가 없습니다. 한쪽에서만 나오면 컬렉션 설정의 분석기와 사용자 사전, 또는 리랭커 설정을 조정합니다.

정기 점검​

Deep Connector는 검색 결과가 맞는지 스스로 판정하지 않습니다. 담당자가 질문과 기대 근거를 정해 두고 주기적으로 확인합니다.

  1. 자주 묻는 질문 10~30개로 RAG 평가 데이터셋을 만듭니다(실험: RAG 평가 참고).
  2. 문서를 교체하거나 설정을 바꿀 때마다 같은 데이터셋으로 실행합니다.
  3. 실행 이력의 점수가 떨어졌으면 결과를 내려받아 어떤 질문이 틀렸는지 봅니다.
  4. 관리자 적재 현황에서 실패한 문서가 없는지 함께 확인합니다.

점검 기록 예시입니다.
