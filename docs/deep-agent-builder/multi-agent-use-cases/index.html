Deep Agent Builder 멀티에이전트 유스케이스

멀티에이전트는 한 에이전트가 모든 작업을 직접 처리하기보다, 목적이 분명한 작업을 서브에이전트에 맡기고 결과를 다시 사용하는 구조입니다. 이 페이지는 현재 확인된 실행 경계를 기준으로 어떤 업무에 적용할 수 있는지 설명합니다. 연결과 저장은 서브에이전트 할당하기, 실행 경계는 멀티에이전트 실행 흐름을 먼저 확인하세요.

어떤 작업을 분리할 수 있나요​

서브에이전트로 분리하기 좋은 작업은 부모 에이전트의 전체 목표와 구분되고, 결과를 독립적으로 확인할 수 있어야 합니다. 현재 근거가 확인된 적용 유형은 에이전트 구성 보조, 문서 작성, 평가 케이스 실행, 산출물 후속 처리입니다.

적용 유형서브에이전트가 맡는 일부모 에이전트가 확인할 결과
에이전트 구성 보조목적에 맞는 서브에이전트 후보를 정리하고 중복을 제거추천 목록과 사용자 승인 상태
문서 작성문서 관련 작업을 전용 작업 폴더와 문서 도구로 처리저장된 파일 또는 다운로드 링크
평가 실행여러 평가 케이스를 분리해 판정하고 결과를 다시 모음케이스별 결과 목록과 종합 결과
산출물 후속 처리서브에이전트가 만든 산출물을 필요할 때만 부모가 조회산출물 식별자, 유형, 제목, 본문

이 표는 업무를 자동으로 병렬 실행한다는 보장이 아닙니다. 실제 실행 가능 여부는 연결된 자원과 실행 시점의 권한 검사, 각 그래프의 구현에 따라 달라집니다.

에이전트 구성을 보조하는 경우​

에이전트를 만드는 과정에서는 Assistants가 사용자 범위의 생성 세션에 도구, 미들웨어, 스킬, 서브에이전트, 프롬프트, 구성값을 채우는 흐름을 보조합니다. 서브에이전트 추천은 유지하기로 한 항목과 UID 또는 이름이 겹치는 뒤쪽 후보를 제거하고, 사용자가 확인할 추천 결과를 만듭니다.

이 유형은 후보를 찾고 정리하는 데 적합합니다. 추천 결과가 곧 연결 저장을 뜻하지는 않습니다. 사용자의 승인과 생성 세션 저장을 거쳐야 하며, 연결 대상은 호출자 소유, 비보관, 일반 에이전트라는 조건을 통과해야 합니다. 추천 목록에 나타났다는 사실만으로 해당 자원을 사용할 권한이 있다고 판단하지 마세요.

완료 여부는 추천 목록의 모양이 아니라 다음 상태로 확인합니다.

  1. 추천 후보에 중복 항목이 남아 있지 않은지 확인합니다.
  2. 사용자가 추천을 승인했는지 확인합니다.
  3. 생성 세션에 저장된 서브에이전트 참조 목록을 다시 확인합니다.
  4. 실행할 때 직접 연결된 서브에이전트가 권한 검사에 포함됐는지 확인합니다.

추천이 비어 있거나 저장이 거부되면 후보가 없다고 단정하지 말고 소유권, 보관 상태, Super Agent 여부, 자기 참조와 순환 참조를 차례로 확인합니다.

문서 작성 작업을 맡기는 경우​

문서 작성 모드에서는 문서 관련 작업을 전용 서브에이전트에 맡길 수 있습니다. 작업 폴더가 있는 문서 작성 서브에이전트에는 문서 작성용 위임 표지가 붙고, 문서 도구와 작업 폴더를 사용해 Office 파일을 만들거나 수정합니다. 완성된 파일은 Canvas에 저장하거나 채팅 첨부로 내보내는 경로가 서로 다르므로 목적을 먼저 정해야 합니다.

이 유형에서는 저장과 다운로드를 같은 결과로 취급하지 않는 것이 중요합니다. Canvas 저장은 작업 폴더의 파일을 Canvas 루트에 커밋하는 동작이고, 내보내기는 파일을 채팅 첨부로 등록하는 동작입니다. 서브에이전트가 반환한 다운로드 링크는 원문 그대로 전달해야 하며, 링크 앞에 다른 접두사를 붙여 형식을 바꾸지 않습니다.

작업 폴더가 없는 degraded 경로에서는 문서 도구를 사용할 수 없는 일반 모드로 실행되고 경고가 남습니다. 따라서 문서 작성 작업을 시작하기 전에 작업 폴더와 문서 모드가 실제로 준비됐는지 확인해야 합니다. 파일 링크가 보인다는 사실만으로 저장된 위치나 다운로드 성공을 서로 대신 확인할 수는 없습니다.

여러 평가 케이스를 나누는 경우​

평가 패널 계약에서는 평가 케이스 수만큼 분기를 만들고, 각 분기의 결과를 결과 목록으로 다시 모읍니다. 케이스별 판정이 서로 독립적일 때 이 구조를 사용하면 한 케이스의 입력과 결과를 다른 케이스와 섞지 않고 확인할 수 있습니다. 이 계약은 평가 패널의 분기와 reducer 동작을 설명하는 근거이며, 현재 Backend 전체 실행 경로가 모두 이 방식으로 동작한다는 뜻은 아닙니다.

이 유형에서 부모가 확인해야 할 것은 분기 수가 아니라 결과가 모두 모였는지와 각 결과가 어느 케이스에 대응하는지입니다. 평가 결과 목록이 만들어졌다고 해서 실제 모델 품질이 자동으로 보증되는 것은 아닙니다. 평가 데이터, 평가자 설정, 실행 상태와 결과를 별도로 확인하세요.

산출물을 후속 작업에 사용하는 경우​

서브에이전트가 task 결과로 만든 산출물은 사용자에게 원본 결과로 한 번 표시되고, 부모 모델에는 짧은 placeholder로 전달됩니다. placeholder에는 산출물 식별자, 유형, 제목, 본문 문자 수와 필요할 때 원문을 조회하라는 안내가 포함됩니다.

부모가 원문을 다시 읽어야 할 때만 부모 전용 산출물 조회 경로를 사용합니다. 조회 결과에서는 표시용 태그가 제거되므로 같은 산출물이 다시 카드처럼 렌더링되지 않습니다. 반대로 원문이 필요하지 않은 후속 작업에서 자동 조회를 기대하면 안 됩니다.

이 유형의 완료 조건은 세 가지입니다.

  • 사용자에게 보인 원본 산출물과 부모가 받은 placeholder를 구분할 수 있습니다.
  • 부모가 조회한 산출물이 원래 산출물 식별자와 일치합니다.
  • 조회한 원문이 사용자 화면에 중복 렌더링되지 않습니다.

적용하지 말아야 할 경우​

다음 조건이면 멀티에이전트 구성을 늘리기보다 단일 에이전트 흐름을 먼저 검토합니다.

  • 부모와 서브에이전트의 책임을 나눌 수 없습니다.
  • 결과를 어떤 입력이나 작업에 대응시킬지 확인할 수 없습니다.
  • 실행 시점에 필요한 model, tool, middleware, skill 또는 서브에이전트의 권한을 확인할 수 없습니다.
  • 문서 작성 작업인데 작업 폴더나 문서 도구가 준비되지 않았습니다.
  • 산출물 원문이 필요한데 부모 전용 조회 경로와 식별자를 보존하지 않았습니다.

멀티에이전트의 수를 늘리는 것이 결과의 정확성이나 실행 성공을 보장하지는 않습니다. 분리한 작업마다 소유권, 권한, 결과 전달 경계를 확인할 수 있을 때만 구성을 확장하세요.
